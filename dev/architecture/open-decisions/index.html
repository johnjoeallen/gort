    Open decisions¶

    Each item gives the alternatives, the trade-off and a recommended direction. A recommendation is not a decision: it is what to build first and test.

    D1. Where continuation lowering happens¶

    • At module compile. Every function is lowered to the Level-0 convention; the module's C and object are final. Pros: fast incremental builds, no IR needed to link, predictable. Cons: no cross-module frame fusion.
    • At application link. Modules ship IR only; lowering runs on the whole program. Pros: best optimisation. Cons: slow links, requires IR from every dependency, weak caching.
    • Both (recommended). Lower at module compile. In optimised mode, re-lower only chains whose inlining or fusion changes them, using retained Tier C IR.

    Recommendation: both, with module compile authoritative. Release a first compiler that does only module-level lowering.

    D2. Locals whose address a callee holds, and the lazy shape¶

    The lazy strategy copies locals into a frame only on a park, which moves them. A pointer to a moved local dangles. With no borrow type (D18) the case is a raw pointer to a stack local; a Ref<T> is not affected, because it owns a count on a slot that never moves. See suspension.

    • Frame-resident locals; the function uses eager frames (recommended). Correct; loses the lazy saving for functions with address-held-across-park locals.
    • Pin the local's storage in the task arena. The local is in the arena from the start, not the stack. Cheaper than a full frame; one more arena operation.
    • Forbid passing a local's address across a park. Simple; too restrictive (conn.recv(buf)).

    Recommendation: the first, then measure how many hot functions it affects. The toy benchmarks did not include this.

    D3. The minimum IR for cross-module optimisation¶

    Alternatives: (a) full typed IR for all functions; (b) IR for functions under a size threshold and generic ones only; (c) author-marked inlinable functions only.

    Recommendation: ship (b) by default as Tier B plus a size-limited Tier C, with the full IR as an option for libraries that want fusion. Measure size against build gain before deciding the default. Minimum requirements on any IR: explicit ownership operations, call-site effects, park points, cleanup scopes, source-independent.

    D4. Representing effects in public interfaces¶

    Alternatives: (a) infer everything and export it (current plan); (b) require the author to declare the effect of public functions; (c) infer, and let the author optionally assert it.

    (b) reintroduces colouring. (a) alone lets an implementation change ripple silently through dependants. Recommendation: (c) - an optional [nopark] assertion (see suspension 1.1), plus tooling that prints the contract diff between versions, and a version policy that treats widening as breaking. Open: whether the attribute form should also replace the existing parks modifier (extern fn[parks]) and extern blocking (extern fn[blocking]) for consistency, and whether to allow parks on non-extern functions as a "may park" promise for stability.

    D5. Recursion and dynamic dispatch¶

    Recursion: SCC fixed point; per-activation frames; depth-counter fallback to frames on the fast path (see suspension). Dispatch: declared bound, default May. Open: the depth limit, and recursion through interfaces where the bound is the only information. Recommendation as written on those pages; test with a recursive-descent parser handler and a visitor over a tree.

    D6. Generics: monomorphisation or shared code¶

    Monomorphised: exact frames and effects, requires Tier B IR, code growth. Shared with dictionaries: no IR dependence, slower, hard to give generic frames a layout. Recommendation: monomorphise; revisit if code size hurts.

    D7. Can frame fusion work across separately compiled modules¶

    It can only when the callee's IR is present (Tier C) at link time. It cannot at module compile. If the callee's module ships A+B only, fusion simply does not happen across it. Alternative: export a fixed frame layout for chosen functions so callers can embed them without IR. This freezes the layout (breaking ABI to change). Recommendation: fusion at link time from IR only; no fixed layouts. Measure the benefit before building it: the toy numbers suggest about a nanosecond per call.

    D8. Debugging, stack traces and profiling¶

    A parked task's native stack is gone; the logical stack is the frame chain. Fusion, lazy frames and inlining make logical frames not correspond to physical ones.

    • Park-point tables in every module (recommended): (frame type, state) -> chain of logical frames with source locations, as DWARF-style inline info. Tooling walks the frame chain for parked tasks, and the native stack plus the chain for running ones.
    • Profilers sample the native stack and append the chain. Needs a runtime hook.
    • Alternative: no maps; stack traces show only physical frames. Cheap, poor for diagnosing the "may park" chain which principle 10 demands tooling show.

    D9. Dynamic module loading and whole-program optimisation¶

    Aggressive devirtualisation and fusion assume a closed world; plugins break it. Alternatives: no dynamic loading; open interfaces declared in build configuration; a runtime flag that turns off closed-world assumptions entirely. Recommendation: no dynamic loading in the first compiler; keep bound-based dispatch so it can be added with open interfaces declared in configuration.

    D10. Blocking FFI¶

    Offload pool, dedicated thread, or run on worker. See the table in dispatch. Recommendation: nonblocking where possible; extern blocking offload by default; watchdog diagnostics.

    D11. Versioning module compatibility and native caches¶

    Format, ABI, contract hashes, cache keys as in modules. Open: whether the compatibility policy is enforced by the compiler (refuse a minor-version consumer of a major-breaking producer) or only reported; how long caches live; reproducible builds and cache portability across machines.

    D12. Cancellation as a non-exception¶

    Recommended: not in throws, not catchable, runs cleanups. Alternative: a catchable exception that must be rethrown. Interacts with the exception model (spec 10.7), and with child-vthread scopes.

    D13. Runaway non-parking code¶

    Decided by the author: the compiler inserts slice checks only in functions marked [yield], or in a type (struct Parser[yield]) or, once packages exist, a package whose default is [yield]. The innermost level wins: function, then type, then package. [noyield] overrides an enclosing default; [nopark] asserts that nothing parks. With no attribute nothing is inserted. Mechanism and rules: suspension 1.1. Loops add no effect by default, so the library-tagging burden an earlier default-on design carried is gone.

    The price is that unmarked CPU-bound code can stall a worker and cannot be cancelled. Mitigations, all Direction: loop warnings with an advisory loops class in the module summary (suspension 1.3), a watchdog diagnostic that reports a worker making no progress past a threshold and names the function it is in (it reports and does not interrupt), and the type-level (later package-level) default for CPU-heavy code. Open: the package notion itself, and whether the attribute spelling should be unified between functions and types.

    Still open:

    • Overhead of a check in a [yield] loop. Unmeasured; strip-mining and small-bound elision are expected to keep it low. Benchmark B13.
    • Slice unit. An iteration counter (cheap, not time) against a timestamp or a flag set from another thread. Recommendation: counter, sized in iterations per check block; the watchdog flag later.
    • Lambdas inheriting the enclosing function's setting.
    • Default revisited. Whether checks should become the default later, once B13 and a real compiler show the cost and the ripple. The earlier design made them the default and was reversed before any implementation.
    • Interaction with the lazy shape. A check is a park point inside a loop, so the loop's live values must be spillable; a loop with locals whose address a callee holds falls under D2 too.

    D14. Packages and imports¶

    Direction, following the Java folder convention; the details are open. Every sample .gort file starts with package name.

    • Rule used in the samples. A package is a folder. Its name is the folder path under the source root (gort/) with dots for slashes, so gort/redis/ is redis and gort/http/styles/cpp/ is http.styles.cpp. Every file in the folder starts with the same package line, and the compiler rejects a file whose package line does not match its folder. A package compiles to one .smod named after it. Declarations are visible across the files of a package with no import. import other names another package, so import redis.types inside redis is gone and import runtime.leaves became import runtime.
    • Package default. [yield], [noyield] or [nopark] is written on the package line, package[yield] imaging, and repeated on that line in every file of the folder. All files must state the identical line; a file that differs or omits it is an error. There is no special file. Alternatives: the attribute in one file only (hidden action at a distance, and one file becomes special), a package-info-style file (rejected), or in a build manifest (the setting is no longer visible in source). Recommendation: repeat it, since the repetition is a few tokens and keeps the setting visible wherever the code is read. Open: the compiler could instead infer the line from the folder and only require the attribute to be repeated.
    • Style variants. http/styles/{cpp,java,mixed}/server.gort are now separate packages (http.styles.cpp, ...), each of one file, which import http and import runtime. They are alternatives and not compiled together.
    • Import granularity. Whole package (used here), or named symbols (import runtime.Conn). Whole package is simpler; symbol imports give the contract hashes in .smod a natural unit, and they are already per symbol there. Recommendation: whole package at the source level.
    • Visibility. What a package exports to others, and how encapsulated sync code (spec 7.2) is protected from being bypassed. Not specified yet.
    • Nesting. Dots mean folder nesting. Whether a nested package can see its parent's declarations (Java: it cannot) is undecided; recommendation: it cannot.
    • Versions. The .smod carries the package version (modules); how a source tree states which version of an imported package it expects.

    D15. Growable arrays, relocation and stable references¶

    Direction, proposed by the author and not yet prototyped beyond the HTTP buffers. A growable array can move its backing store when it grows. The rule that keeps every reference safe is that no reference into a growable container is a raw address.

    • Handle. A growable container (T[], string builder, map storage) is a small header that never moves: {ptr, len, cap} plus, when the container is shared, its lock word. Only the backing store behind ptr moves; growing updates ptr in place. This is the shape Ref<T> already has (an individually allocated object that stays put).
    • Interior references are (handle, offset). &v[3], a slice, an iterator and a stored cursor name the container and a position. They cannot dangle, so let r = &v[0]; v.push(x); use(r) is legal and correct. This is the offsets rule of the HTTP prototype (a Request is a pair of offsets), applied by the compiler instead of the programmer.
    • Deref window. The raw address exists only inside a window in which the compiler has loaded ptr and nothing can move the store.
      • Shared container: the window is the sync or mutate block (spec 7.3, R1 and R4). Growing needs mutate; a reader inside sync therefore excludes a grow.
      • Unshared container: no lock (R6). The window ends at any call whose mutation summary says it may grow the container, and at every park point. After that the compiler reloads ptr. Calls through interfaces, function values or foreign code are treated as may-grow.
    • Only growable containers get a handle (superseded in part by D17). Plain structs and objects were to be referenced directly, since indirection would cost locality and an allocation per object for no safety gain. D17 gives every new T object a never-moving control block anyway (it carries the counts), and proposes that the body behind it may move for memory reclamation, so the cost argument changes to one extra load.
    • Effect on D2. No raw array address is frame-resident across a park (a locked window cannot span one, and an unlocked window ends at the park), so pointers into growable arrays do not force an eager frame. Borrows of other locals are still D2.
    • Contract. The mutation summary in the .smod (modules.md, "Access and escape summaries") gains a may-grow bit per container parameter, so a caller can end its deref window exactly. Widening it is a breaking change.

    Costs and open points:

    • One dependent load of ptr per access outside a hoisted window. Measured, micro-benchmark only (handle.md, B14): reloading on every access is not visible at -O2 and equals a raw pointer when hoisted. At -O3 a window that ends every iteration costs vectorisation (about 0.14 to 0.23 ns/element in L1), and a may-grow call in the loop costs the call (0.7 to 0.9 ns), not the reload. A second run with realistic bodies and a lock around every variant (handle_real.md) gives a typical loss of 1 to 3% (0.01 to 0.3 ns per element) over a raw pointer for bodies that do work, individual configurations up to about 10%, and up to +28% only for an almost-empty body with no lock (0.25 ns); the noise floor is up to 19% in a few cells because gcc compiled two identical loops differently. One machine, single thread, uncontended locks, synthetic windows, A third run, a mixed request on the C runtime with a lock-protected cache, a simulated database wait and growable-buffer rendering (mixed.md, B12), found the handle build within noise of a raw pointer in work per request, throughput and latency (0.5 to 3% run-to-run spread; worst case +2.1% for the pessimistic reload-at-every-access build). So what remains open is how often real windows end, which needs a compiler.
    • FFI. C needs a stable address. An extern call takes a pinned pointer: the container is excluded from growing for the call. A library that retains the pointer needs a non-moving allocation (a fixed-capacity array or a dedicated virtual region), declared in the binding contract (spec 5.2).
    • Large arrays. A dedicated virtual-address reservation grows in place, so its ptr never changes and its handle test is free. Whether to use one is the older question in open questions; it becomes an optimisation under this rule, not a correctness requirement.
    • Precision of the may-grow summary. A coarse summary ends windows too often. Start per container parameter; refine only if B-series results show it matters.
    • Stable identity beyond arrays. For objects that other objects point to (graph nodes), use Ref<T>: it never moves.

    D16. Composition and interfaces instead of inheritance¶

    Direction, proposed by the author; no prototype. A struct is built from other structs and interfaces. There is no class inheritance.

    struct Dog: Animal with Body {
    fn name(): String { return "dog" }
}
    • : Animal lists interfaces (the colon reads as in x: T and a generic bound T: Animal: Dog satisfies Animal). The struct must provide every function the interface requires. An interface may give default functions (behaviour, no data), so it can share code without sharing fields. A struct converts to any interface it implements. This is the only subtyping.
    • with Body lists structs. Each is stored inline in the new struct, as a field, and its fields and functions are promoted, so dog.feed(1.0) forwards to the Body. Promotion is shorthand for writing the forwarding functions: no new type relation and no layout prefix rule, so no slicing. A plain field body: Body is not embedded and promotes nothing. Both parts are optional (struct Dog: Animal, struct Dog with Body, struct Dog: Animal, Named with Body, Tail). No keyword is reserved for it (is is left free for a possible type test).
    • No open recursion. A function of Body that calls feed calls Body.feed, never a Dog override. Dynamic dispatch exists only at an interface call. A Dog function with the same name as a promoted one hides it for callers of Dog and does not change what Body does internally.
    • Why not class inheritance. Open recursion turns every self-call into a dynamic call, and calls through interfaces compile against a declared effect bound (default may-park). That would degrade the may-park inference, the [nopark] and lock-body checks, and the access summaries the sharing rules use, program-wide. It is also where fragile-base-class bugs come from.
    • Fallback if examples need it: a sealed single-inheritance base with override, where the compiler sees the whole hierarchy and can keep the effect precise.

    Open points: the name of the inline field (dog.body?); clashes when two incorporated structs promote the same name (compile error until the author disambiguates); whether with may name an interface-typed field; cleanup() order (fields in reverse order of declaration, incorporated structs in the same order); how interface access modes (sharing, sync/mutate) are stated; and whether : Animal can be declared outside the struct (as Go and Rust allow) or only in its header.

    D17. Moving objects between chunks: split control blocks, and weak promotion¶

    Status: the split control block and the moving of bodies between chunks are rejected for counted objects by D18; the measurements below are the evidence. weak.promote() returning Ref<T>? stays. Direction, proposed by the author; unmeasured. The finding that motivates it: long-lived objects scattered through shared chunks pin memory (Measured, group2.md: 6 to 11x retained after a burst). Per-type arenas separate types, not lifetimes, so a type that mixes short and long lifetimes still pins chunks. Chunked arenas already let a type arena grow without moving anything; this decision is about shrinking.

    • Split. The control block (strong and weak counts, metadata, a pointer to the body as {chunk, offset}) lives in one fixed-size control-block arena shared by all types, and never moves. Ref<T> and WeakRef<T> point at it. The body (the fields) stays in the type's chunked arena and may be moved to another chunk by copying it and updating the one pointer in the control block. No Ref or WeakRef changes, and counting never touches the body.
    • Lifetimes. When the strong count reaches zero the body is destroyed (cleanup() runs) and its slot freed. The control block stays until the weak count is also zero. Today's layout (spec 3.3) keeps the whole slot until then, so a dead object with a lingering WeakRef pins its full size; after the split it pins only the control block (about 32 bytes). A WeakRef that is never dropped, for example in a long-lived cache, pins that block until its holder drops the entry; holders should drop an entry when promotion fails.
    • Weak promotion returns Ref<T>? (null if the object is gone). Expiry is an expected result the caller must handle, as in Java's WeakReference.get(), Rust's Weak::upgrade and C++'s weak_ptr::lock. Both ways of keeping the data fail identically, because the object is already destroyed at strong zero, so holding the bytes would not avoid the failure. There is no implicit promotion and no ExpiredReference (spec 3.1).
    • When a move is safe. An unshared object: between turns of its owning worker (scheduling is cooperative, so no raw address is live there). A shared mutable object: under mutate, which excludes the sync readers. A shared immutable object: after a grace period, once every worker has passed a park or yield. An object passed to FFI is pinned (as in D15). A pointer held in a frame across a park (D2) holds a raw body address: either it blocks the move or it is stored as (control block, offset).
    • A visible service, not magic (principle 10). Compaction is a runtime service with a stated policy (evacuate chunks below an occupancy threshold), a bounded step per pass, and statistics. Whether it is on is a per-type choice.

    Costs and open points:

    • One extra load (control block then body) per dereference outside a hoisted window; B14 measured about 0 to 3% for such a load in realistic bodies, but not on pointer-heavy object graphs.
    • new becomes two allocations (control block and body), which could roughly double its 5 to 10 ns. Types that do not opt in could keep the combined slot of 3.3; two layouts cost compiler complexity.
    • Allocation epoch in the control block (Direction). The slot header has a 32-bit allocation epoch, packed into meta beside the worker index so the header does not grow and the layout is the same in every build. It is filled in only when age tracking is on (--track-age, implied by --debug), from a global epoch counter that a ticker advances (no clock read in new); otherwise it is 0, meaning unknown. Because release builds leave it empty, nothing in the runtime may depend on it: it is for age histograms and finding leaks. With D18 nothing moves, so there is no mover to use it.
    • Tiny objects (about 16 bytes or less) gain little: the control block is a large fraction of the body. They could live inline in the control block.
    • Generations may become unnecessary for object arenas: a Ref points at the control block, so validity comes from the counts, and the chunk-epoch fix for decommit (group2.md, section 7) would apply only to the control-block arena. Check before relying on it.
    • Measured, micro-benchmark only (split.md, B15; single thread, hand-written C):
      • Time (loss). new is 9 to 45% slower, a free 58 to 135% slower, a free-plus-allocate pair about 2x. A dereference through the control block is 13 to 97% slower for independent reads and 75 to 174% slower on a pointer chase (two cache lines in two arenas). This is much more than the D15 header (0 to 3%), which sits next to its array.
      • Memory (gain). Dead objects held by a WeakRef: 157 MB falls to 50 MB (64 B bodies), 263 MB to 25 MB (256 B). After a burst leaving 1% scattered survivors: 44 MB with moving, 70 MB with page release only, 157 MB with nothing. At 10% survivors only moving helps (64 MB against 157 MB).
      • Memory (cost). A live object is 96 B against 80 B for a 64 B body (+22% on a full heap), and the control blocks of scattered survivors stay pinned (about 24 B each), which is the floor of the 44 MB.
      • When it pays. Not when objects die roughly in allocation order (nothing is retained and the split is pure cost); for types with mixed lifetimes and for long-lived WeakRefs.
    • Measured, a whole service (service_split.md, the mixed-request service with a cache of Ref<User> objects):
      • Time (loss). Work per request +4 to +12% with one worker and +6 to +27% with four; throughput -2 to -10% (one worker) and -16 to -21% (four) where requests are served from the cache; no difference where the service waits on its database. With four workers the longer critical section (a second dependent miss inside sync) raises failed lock attempts per request from 3.9 to 7.0.
      • Memory. Steady state is 14 to 17% larger. After 90% of the cache is evicted at random and traffic narrows, only moving returns memory: 44 MB resident at the end against 54 MB for the combined layout and 63 MB for the split without the mover.
      • Moving while the service runs. Readers exist only inside sync, so a move takes mutate on the cache lock for one chunk at a time (longest hold 48 us); no grace period or epoch tracking is needed. 54,000 bodies cost 48 ms of mover CPU and about 7% of the workers' throughput while it ran.
    • Measured, sharded locks and clone-on-hit (b12_ref.md, the same service with 16 cache locks and a hit that clones the Ref and reads the body after leaving the lock):
      • Time (loss). Most of the four-worker loss above came from the single lock. With 16 locks the split costs +4 to +10% work per request over the combined layout (one worker: +7 to +10%) and 0 to -8% throughput; failed lock attempts per request fall from 6.3 to 0.15. The remaining cost is the second dependent cache miss per hit (about 35 ns).
      • Clone-on-hit is not measurably slower for the combined layout and 0 to 1.5% cheaper for the split (a shorter critical section). With half the requests on 1,000 hot users the atomic count updates cost about 5 ns per request.
      • Moving with clones. A move takes every shard lock and skips a chunk if any of its objects has strong > 1 or is held by a request alone. The flush scenario still ends at 49 MB resident against 63 MB (split without the mover) and 54 MB (combined); 1 of 330 chunks was skipped, because a request holds its clone only across a non-parking render. A Ref held across a park (D2) would pin chunks far more often: not measured.
    • Measured, a Ref held across a park and Refs held for good (hold.md):
      • Held across a park (100 us to 10 ms after every hit): no cost in steady state, and the mover recovers the same memory (35 MB resident at the end against 63 MB without it) while wasting up to about 78% of its attempts on pinned chunks.
      • Held for good (a Ref stored somewhere long-lived): with 0.1% of hits keeping their Ref the mover recovers 9 MB instead of 14 MB (54 MB at the end, against 49 MB without stashing and 63 MB with no mover), and at 1% nothing, because a scattered pin blocks its whole chunk. The mover is all-or-nothing per chunk; moving only the unpinned bodies was not tried.
      • For D2. A Ref held across a park needs no special rule for moving; a stored Ref is the case that defeats it.
    • Consequence for the direction. Page-level release of free pages costs nothing at dereference and gets most of the gain at 1% survivors, so it comes first. The split is opt-in per type (the fixed combined slot stays the default), aimed at mixed-lifetime types and WeakRef targets. Not measured: moving only the unpinned bodies of a pinned chunk, concentrated (rather than random) long-lived Refs, mutable shared objects, a single very hot object, and a service with real sockets.

    D18. Memory model: values, handles, chunks, arrays, scopes and C interop¶

    Direction, decided by the author in a design review of the memory-model concept (Gort Memory Model: Concept) and the discussion after it. Items marked Open are not decided. Costs are from the B15 and B12 runs unless stated; nothing here is implemented. This section was consolidated from decisions first recorded one at a time; where it differs from an earlier wording, this text wins (a control block on every new object; a field is a scalar, a handle or an inline struct value; no language-level hoisting).

    1. Values and handles.

    • A scalar is a plain value: integers, floats, bool, Duration, Instant and the like.
    • A handle is a counted reference: Ref<T>, WeakRef<T>, String, Array<T>. Every handle owns a count. A copy or a pass increments it; a drop (scope exit, reassignment, container removal) decrements it. There is no count-less reference that can be named or stored, and no T&; the one unnamed exception is a method's receiver place (item 1, struct values). A Ref<T> always keeps its slot alive, so it cannot dangle, and a slot never moves, so a Ref needs no frame-residency rule across a park. The cost is one increment and one decrement per pass or copy (non-atomic when unshared, item 7); unmeasured.
    • A field is a scalar, a handle or a struct value (decided; reverses the earlier "scalar or handle" rule). A field whose type is a struct and is not wrapped in Ref is stored inline in its container: Line { a: Point, b: Point } is one body holding both points, with no separate allocation, control block or pointer chase. A field written Ref<Point> is a handle to a separate counted object with its own identity. The programmer chooses by what is written, as for locals and parameters. Inline nested values make the container's body (and so its chunk unit) larger, they have no identity of their own (no Ref can name line.a; Ref<Point> p = line.a is a copy into a new object), and they are locked with their owner (a write to line.a.x needs the block of the owner, as for an array element). Which fields should stay Ref is a per-field choice: a field that other holders share, or that has identity, is a Ref; a part that the container exclusively owns is inline. Library containers (Map, OrderedSet) and String and Array are handles, so Store.entries stays a Ref<Map<...>>.
    • A counted object is a control block (counts, metadata) plus a body, allocated as one unit in a chunk of that unit type. Every new makes one (item 5). It never moves.
    • A struct body without a control block exists in four places only: as the body of a counted object, as an inline field of another struct body, as an element of an Array<S> run (item 3), and as a local on the stack. a[i] of an Array<Customer> is a Customer, not a Ref<Customer>, and no Ref can name one element. An Array<Ref<Customer>> is a run of handles to separately allocated objects that happen to be Customer.
    • Struct values (decided; direction from the author, the two marked recommended are the model's proposals). Ref<> and Array<> are language elements, not library generics, so the compiler knows what an Array<Point> is. A struct with no Ref around it is a value: it can be a local, a parameter, a return, an Array<S> element or the body of a counted object, and it is passed and assigned by value.
      • Point to Point copies the body. Ref<Point> to Point copies the body out. Point to Ref<Point> allocates a new counted object and copies the body in; this should require an explicit new so the allocation is visible (recommended).
      • The copy is field by field and recursive through inline values, generated by the compiler: scalars are copied, each handle field (at any inline depth) is copied and takes a count, and dropping the copy releases it; the objects behind handles are not copied. A value cannot contain itself by value, so the copy is finite; cycles go through a handle. A struct with many handle fields is costly to copy, so large ones should be passed as Ref<T>; the last use of a local may be moved without count operations (an optimisation).
      • Copying out of a shared object reads every field, so it follows sharing.md R1 (sync if any field is mutable). a[i] is a place, not a copy: a[i].x = 3 writes in the array, and a copy is made only when it is assigned to a local (let q = a[i]; changing q does not change the array).
      • == on values compares state (decided). Two struct values are equal when their fields are equal, recursively through inline values; this is also what makes a value usable as a Map key (equality and hash are derived). == on Ref<T> compares identity. Open points are in item 11: how a handle field inside a value compares, how floats compare, and the syntax for comparing the bodies behind two Refs.
      • A method's self is a place (the body itself), so one method serves Ref<Point>, Array<Point> and Array<Ref<Point>> callers with the same call syntax: r.move(1), a[i].move(1), b[i].move(1). self cannot be named as a type, stored, returned or captured; every conversion to something storable (Ref<Point> q = self, return self) is a copy. This is the only borrow in the language and it is call-scoped. Ordinary parameters stay semantic copies; the compiler may pass them by pointer when the callee never writes them, which is not observable.
      • Mutating self needs the same block as any write: the lock of the Ref for a Ref<Point>, the lock of the array for an element of Array<Point> (an element has no identity of its own).
      • Validity of self: a Ref receiver is held by the caller's count; a fixed or bounded array's run never moves; a growable array's element is pinned for the call (a pin count in the control block, growing a pinned array throws), and the compiler omits the pin when the summaries show the callee cannot reach that array (recommended, open to the author).

    2. Chunks and arenas.

    • Per-type arenas of chunks. A chunk is a single type (the type of its arena) and holds only payload: no header, no boundary tags, no free-list links in freed blocks. Everything that manages a chunk is external: a descriptor (base, size, live count, free-space map) in a table that never moves, found from an address by masking it to the chunk's aligned base. The free-space map is a bitmap whose unit is the type's own size; a run of n adjacent elements is n adjacent free bits, found by a word-at-a-time run search. The size of a block is not stored in the chunk: an object's is its type's, an array's is cap in its control block.
    • No object or array body moves between chunks, and the arena never moves. This rejects D17's split control block and its mover. What D17 measured is the reason: the split cost +4 to +10% work per request with sharded locks (+6 to +27% with one lock), made a steady-state service 14 to 17% larger, and a pointer chase through two cache lines 75 to 174% slower; it recovered memory only after a burst. Returning memory to the OS is left to page-level release of free pages. The cost accepted: a dead object that a WeakRef still names keeps its whole slot until the weak count reaches zero (INV-8).
    • Arrays larger than a chunk get a dedicated oversize chunk. A bounded or fixed-length array gets exactly its run; a growable one gets its run plus headroom (size undecided). An oversize chunk holds one array and is returned whole. Arrays are never split across chunks.
    • Open: a summary level over the bitmap so a run search does not scan a full chunk; the cost of the extra cache line an allocate or free touches (unmeasured); the hot and cold split of the control block from the body (unmeasured).

    3. Arrays.

    • There are no bare native arrays; every array is an Array. An array's control block (counts, absolute pointer to the elements, len, cap) lives outside the object arenas, in a slab of control blocks that never moves. There is one control block layout for every array. The elements are a contiguous run in an ordinary chunk of the element type (no special array chunks); a new chunk is allocated if no run fits. Elements carry no per-element control block (a control block per element was rejected: 16 bytes each, 17x for u8, 5x for i32, no SIMD). An array of handles releases them when it is dropped or an element is removed.
    • Three declarations:
      • Array<type[size]> x = new Array<type> is bounded: capacity size, length 0; you can add up to size elements and no more. Its run is allocated up front and never moves.
      • Array<type> x = new type[size] is fixed length: length size, elements set to the type's default value. Its run never moves.
      • Array<type[]> x = new Array<type> is growable. When it outgrows its run it is reallocated to a larger run (a whole number of blocks; block size undecided), copied, and the control block's pointer is updated; no Ref to the array changes. This is the only movement of payload between chunks, and the program caused it. A growable array is never chained: its elements are always one contiguous run.
      • Array<> x = new type[size] infers the element type. size is any runtime value, not a compile-time constant. A fixed-length array and a bounded array are the same type to a callee.
    • Bounds checks apply to every array; an index outside 0..len, or adding past a bounded array's capacity, is a runtime exception.
    • The array type is written Array<u8>; u8[] in earlier examples was migrated to it, and array literals ([]) and constructors (Row[], T?[](n)) are not yet migrated.
    • Open: whether an array handle is counted and shared by reference or an owned value; whether a growable array converts to a fixed one without a copy (a "frozen" array); the block-size policy; whether array blocks are ever compacted; what a slice buf[..n] is (a view with its own control block that counts the parent, or a copy as for a String substring); the cost of a stack buffer being an Array rather than a raw buffer (B17).

    4. String. String is a language type that behaves like an immutable Ref<Array<u8>>: it is reference counted and its bytes never change, so copying or passing one is a count operation, reading one needs no sync or mutate, and it can be shared across workers freely. It is written String. A byte array is not a string. A string literal "..." is stored in a permanent block, and a String is created that refers to it; that String is counted like any other, but its count reaching zero does not free the permanent block. A substring is a copy out of the parent: new bytes, no count on the parent, so a small substring never keeps a large parent alive. Open: the permanent-block layout and how the String's control block marks it as not freeable.

    5. new, locals and scope exit.

    • Simple locals (scalars, struct bodies) live on the data stack and are reclaimed at scope exit (spec 4.1). A local that owns counts (any handle) releases them when it is cleaned up: every exit path (return, error, exception, cancellation) runs the drop in reverse order of declaration.
    • A new object is held by a Ref<X> that the compiler injects if the source writes none. a = new X(...) makes an injected local Ref<X> that owns the object; scope exit drops it and the object is freed. In Ref<X> x = new X(...) the explicit Ref takes the place of the injected one. In a = new X(...) followed by Ref<X> x = a, x is a copy (count 2 while both are live); both are locals and both drop at scope exit, so the object does not outlive the scope. The object outlives the scope only when a Ref escapes it: return a where the return type is Ref<X> (the injected Ref is moved out), or a Ref stored into longer-lived storage (item 6).
    • The object is counted from allocation, so there is no static decision at the new site and no problem with a value bound to a Ref on one branch only. The cost is a control block and a count operation on every new, including ones that never leave the scope; a new may be placed on a stack or in task storage, without the control block, only if the compiler proves it cannot outlive that storage (spec 4.4). That is an optimisation, not a rule. Where the compiler is unsure it allocates in the shared arena.
    • The concept's frame-exit promotion (copy a payload that something else still holds into a shared chunk) is rejected: it needs a payload move, so a wrong inference cannot be repaired afterwards and the analysis has to be sound.
    • Open: whether an object placed on the stack under the optimisation can be named by a Ref (its count must reach zero by scope exit).

    6. Escape direction.

    • Passing a local down to a callee, including as an out parameter, does not make it escape: the callee is shorter-lived. A Ref argument still takes and releases a count.
    • Storing a value into storage the caller supplied does escape: that storage is longer-lived.
    • A callee that stores a new object into a container it was passed allocates the object shared, without knowing whether the container is local. Shared is always safe.
    • A value that flows to a return, or into a parameter's contents, is allocated shared up front.
    • A shared or longer-lived object never holds a reference to a local (the concept's INV-7): a store of a local into one is rejected, or the local is published first (sharing.md R5).

    7. Counts. Counts on an unshared object may be non-atomic. They become atomic when the object is shared (the shared flag of sharing.md R5, set before the handoff). Spec Phase 1 starts with atomic counts; this is the later optimisation. The saving is unmeasured.

    8. Access and pointers.

    • Shared objects: a dereference is allowed only inside a sync or mutate block, which cannot contain a parking call (sharing.md R1, R4). No exceptions.
    • Unshared objects need no block for access, and there is no language-level hoisting (decided). Every access goes through the Ref, field or container: a.b.c is a load per hop. A call that removes an object from its container is therefore safe, because the next access sees the container's new state and nothing caches the old address. The injected Ref that earlier drafts used for a hoisted dereference through a container or field is gone, with the borrow rules it needed.
    • An optimisation, not a rule: the compiler may keep a pointer in a register over a stretch of code where it proves no call can drop the object, grow its array or park. This is invisible to the program and needs no Ref. An Array<T[]> base pointer is reloaded after a call that may grow it (the D15 may-grow summary); a park does not invalidate a pointer into an unshared container, because no other virtual thread can reach it.
    • deref() is unsafe. It yields a raw pointer that the checker does not track: it can dangle after a drop, a reassignment, a may-grow call or a park, and the program is responsible. deref() may be called only inside an unsafe block; there is no unsafe function. It is not allowed on a shared object outside sync/mutate, even inside unsafe.
    • Exception: a raw pointer to a stack local across a park. Under the lazy frame shape the park moves the local into a frame, so the pointer dangles. That is D2: the function uses an eager frame, or the local is pinned in the task arena. A Ref is not affected.

    9. Dispatch. Gort has no virtual dispatch on struct functions, no inheritance and no open recursion (D16); a call is dynamic only at an interface call or a function value. A direct call has an exact escape and effect summary. An interface or function-value call takes the join of its possible targets' summaries, or a conservative summary (arguments escape, bound may-park) when the target set is not known (separate compilation, dynamic loading, D5, D9). Open: whether the compiler may join over every implementation it can see in one application link (closed world), or always uses the conservative summary.

    10. Passing data to C.

    • Everything passed to C is a copy in standard dynamic storage, of a C-compatible type (decided). The Gort object itself is never handed to C. The copy comes from a dedicated allocator over the normal C runtime heap (malloc) and is freed at the end of the enclosing scope unless a retained parameter took it. The types that cross are C-compatible only: scalars, C-layout structs of them, raw pointers and sizes. A Ref, Array, String, WeakRef or any other handle cannot be a parameter or a field of a C-visible struct; the compiler converts at the call (a String to a NUL-terminated char * copy; an Array<T> of scalars to a copy of its block) or rejects the call.
    • No size is passed with an array's block. If the C function takes a length, the developer passes it (c_crc32(buf, buf.len())).
    • retained (decided). An extern parameter may be declared retained: C keeps the pointer after the call. That buffer is not freed at scope exit; C owns it, and the program releases it through the library's API.
    • The copy does not make the call safe. C can write past the end of what it was given and cause a memory error. The extern declaration is a promise, as it is for parking (sharing.md R8), and the call is in an unsafe context. This keeps C-visible memory out of the arenas and lets C-side free conventions work.
    • Open: the cost of the copy and the C-heap allocation per call against pinning (unmeasured; a small-buffer fast path is possible); how an extern declaration states the size of a buffer it takes, so a bounds check can be placed on the Gort side.

    11. Open, in one list.

    • Equality of values (item 1). A handle field inside a value: compare by identity (same object) or by the state behind it? Recommended: identity, except String, which compares by content because it is immutable. Floats: NaN != NaN would make a value unequal to itself, so compare bitwise or define it. Syntax for comparing the bodies behind two Refs.
    • Struct values (item 1). Decided: parameters and returns of struct type are values passed by copy, so Command, Scan, Line and Payload stay as written. Still open: whether Point to Ref<Point> always needs an explicit new; the growable-array pin; a lint for a local copy that is mutated and then dropped; whether a value method may be declared to take a copy of self instead of the place.
    • Locking. Whether sync(store) covers the objects the Store holds by Ref, or each mutable object has its own lock and is named in its own block. This is the largest open item for the programmer; the sharing.md examples assume the second (sync(m)).
    • Counted against owned array handles; frozen conversion; block-size policy; compaction; slices; stack buffers (item 3).
    • Permanent-block layout (item 4); stack-placed objects named by a Ref (item 5).
    • Closed-world dispatch join (item 9); C buffer sizes and the copy cost (item 10).
    • Summary level, descriptor cache line, hot and cold header split (item 2).

    12. To measure. Non-atomic against atomic counts on a shared-nothing path; a plain per-access load against a count-and-load (B14, B16); readers dereferencing while another thread assigns Refs (false sharing), with the counts on a separate cache line from the body as a switchable layout; stack against arena placement for short-lived new objects; the copy cost of a value with handle fields at depth, and inline nesting against a Ref field for the Redis and HTTP structs (B17); fixed Array<T> run allocation against a general allocator; the cost of two allocations per array. See B16 and B17 in benchmarks.
