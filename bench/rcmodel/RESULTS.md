# Gort refcount-everywhere model: cost vs Go, Java 25, Rust

## 0. Pre-registration (written 2026-11-10T10:30Z, BEFORE any benchmark was run)

Nothing in this section was edited after results existed. Results start at section 1.

### Hypotheses (my priors, stated so they can be wrong)

| # | Hypothesis | Predicted number |
|---|---|---|
| H1 | W1, one uncontended non-atomic inc+dec pair costs roughly the store-to-load forwarding latency, because the dec reads what the inc just wrote. C1 `local` costs 1-2 ns per pass over C0 `raw`. | +1.0..2.0 ns/pass |
| H2 | The shared-flag test is almost free when it is perfectly predicted. C2 on unshared objects is within 10% of C1. | C2/C1 <= 1.10 |
| H3 | An uncontended `lock xadd` costs about 15-20 cycles on Zen 5, so C3 `atomic` costs 3-4x C1 per pass in W1. | C3 = 3..4 x C1 overhead |
| H4 | W2, C2 and C3 collapse when many threads touch the SAME entry (cache-line bounce) and degrade little when each thread has its own hot entry. Uniform keys over 10k entries sit in between. Hot-same at 16 threads is >= 10x slower per op than hot-diff for C2/C3. | see left |
| H5 | W3, most refcount traffic is on request-local objects that are never published, so C2 stays on the non-atomic path except for the shared session table. C2 loses 10-25% to C0 `raw`. | C2/C0 = 0.75..0.90 |
| H6 | W3, malloc/free per object is a large share of request cost in C. Go and Java pay GC and write-barrier cost instead. C2 is not slower than Go at 8 workers; I expect C2 about 1.0-2.0x Go's throughput. | C2 >= 1.0 x Go |
| H7 | C2 vs Rust-pessimal (`Arc` clone on every pass): C2 wins, because Arc is always atomic and C2 is not. C2 vs Rust idiomatic: Rust wins by 10-30%. | |
| H8 | Of the C2-vs-C0 gap in W3, inc/dec traffic itself is the largest share (>60%), the flag test is the smallest (<10%), atomics are the remainder. | traffic > atomics > flag |
| H9 | W4, cascading free of 1M nodes costs about the same as, or less than, Go/Java GC amortised over a build/drop cycle. WeakRef back-pointers add 10-30% in C. | |
| H10 | C4 `elided` removes most of the C2-vs-C0 gap in W3 (C4/C0 >= 0.95). | |

Where I expect to be wrong: H6 (Go may be closer than I think), H3 (Zen 5 atomics may be cheaper), H4 (the stripe lock in the table may dominate contention and mask the count bounce).

### Decision thresholds (verbatim from the brief)

Compared with Go on W3 at 8 workers (ratio R = Go requests/sec divided by C2 requests/sec, so R <= 1.5 means C2 is within 1.5x):

- C2 (`flagged`) within 1.5x of Go throughput (R <= 1.5): **model is viable. Continue.**
- C2 between 1.5x and 2x (1.5 < R <= 2): **viable only if C4 (`elided`) gets within 1.3x, and the elisions are the kind a compiler could realistically do.**
- C2 slower than 2x (R > 2), and C4 still slower than 1.5x: **confirmed not viable. Stay parked.**

Also reported: C2 vs Rust-pessimal (Arc clone per pass), C2 vs Java 25, and the split of the C2-vs-C0 gap between flag test, atomics and inc/dec traffic.

Operational definitions fixed now: "throughput" = median over >= 10 runs of requests/sec in W3 with 8 workers; "gap share" is measured with the variant ladder C0 -> C1 (traffic) -> C2-with-unshared objects (flag) -> C2 as run in W3 (atomics where objects are really shared) -> C3 (all atomic, upper bound on atomics).

## 1.1 Threshold outcome (pre-registered, W3, 8 workers, shared session table)

| | Mreq/s | ratio |
|---|---|---|
| Go 1.24 (GOMAXPROCS=8) | 18.1 (15.9–18.5) | 1.00 |
| **C2 flagged (-O2)** | **31.2 (30.6–31.4)** | **C2 is 1.73x Go; R = Go/C2 = 0.58** |
| C2 flagged (-O3) | 31.3 | R = 0.58 |
| C4 elided / C0 raw / C3 atomic | 32.4 / 33.9 / 18.3 | C3 is 1.01x Go (R = 0.99) |
| Java 25 G1 / ZGC | 21.7 / 18.3 | C2 is 1.44x / 1.70x Java |
| Rust idiomatic / Rust pessimal (Arc per pass) | 28.9 / 16.9 | C2 is 1.08x / 1.85x Rust |

**Threshold met: "C2 within 1.5x of Go: the model is viable. Continue."** C2 is not merely within 1.5x of Go, it is faster. The
C4 elision step is not needed to pass. This was true at -O2 and -O3, at 1/4/8 workers (R = 0.80 / 0.74 / 0.58), and with
`work=8` per request (C2 10.7 vs Go 8.15 Mreq/s, R = 0.76). p99 latency at 8 workers: C2 270 ns, Go 1070 ns, Java G1 645 ns.

Caveat on what this does and does not show: it shows that **non-atomic counts plus a flag test, on objects that stay thread-local,
cost 8% against raw C here** (C2/C0 = 0.92 at 8 workers, 0.94 at 1). It does **not** show Gort would beat Go: the C side uses glibc malloc and a
hand-written spinlock table, the Go/Java sides pay GC and idiomatic locking (bias 1 and 2 below), and the request is only ~0.2 µs of work.

## 1.3 What each workload showed (details in the tables below)

* **W1**: C0/C1/C2/C4 are all 0.73-0.98 ns/pass; C3 and C2-with-flag-set are 7.42; Go 0.87-0.92; Java 0.34-0.55 (JIT inlines/collapses
  the chain, so it is not the same work); Rust idiomatic 0.78-0.93; Rust Arc 7.8-8.0. Not-optimised-away check: `results/asm_check.txt`.
* **W2**: every entry in W2 is shared, so C2 always takes the atomic path and C2 ≈ C3 ≈ Rust-Arc; single thread C2 30 Mops/s vs raw 123
  (4x). Uniform keys scale (C2 216 Mops/s at 8 threads, 2.8x below raw); hot_diff scales almost linearly for everyone (C2 482 vs Go 493 at 16);
  hot_same collapses for every implementation using a stripe lock (C 4-10 Mops/s at 16 threads); Go's RWMutex holds 63. **W2's C-vs-Go
  gap in hot_same is a lock-design artefact, not evidence about counts.**
* **W3**: see 1.1. C3 (always atomic, 33 atomic incs per request) is 41% slower than C2 and only matches Go.
  Executed counting ops per request (C2, COUNT build): 33 incs (3 atomic: the shared-session clones), 39 decs, 6.1 mallocs.
  C4 cuts that to 1 inc and 7 decs (elision removes 97% of count traffic) and recovers 4 points (0.92 -> 0.96 of raw).
* **W4**: single thread, C2 costs 23.0 ns/node/cycle vs raw 22.5 (+2%); traverse (passing Refs) 3.9 vs 3.6 ns. C3 29.9. Free cascade
  9.6 ns/node, dominated by `free`. With 8 threads all C variants are memory-bound and the cost of counts is 12-14% (C2 74.9 vs C0 65.5 wall)
  in traverse. Java G1 beats every C variant (18 vs 65-75 ns/node at 8 threads); Go and C2 are in the same range at 1 thread but Go uses more CPU.
* **W5**: all three C servers plateau at ~1.54M req/s with 100+ connections regardless of mode, **so the load generator (oha on 8 cores) is
  the bottleneck and W5 cannot separate C0/C2/C3**; it only says "the Gort-model server is at least 1.75x Go (878k) and 2x Java (785k)
  on this loopback test, with p99 56-70 µs vs Go 643 µs and Java 191 µs at 100 connections". Idle connections (10k): C server 47.5 B each,
  Go 14.3 KB each (goroutine + buffers), Java not measurable (heap sizing swamps it, 19 B). Peak RSS: C 2.2 MB, Go 349 MB, Java 1.7-26 GB.

## 1.4 The three biggest sources of error or bias

1. **Allocator and GC asymmetry, and a thin request.** C and Rust malloc/free every object; Go and Java bump-allocate and collect.
   Allocation is a large share of a 200 ns request, so C-vs-Go/Java is mostly "malloc vs GC" and not "refcount vs trace". It also
   explains W4 (Java 5x faster than C there) and W3's Go-over-C ratio. Also, a real handler is heavier than 0.2 µs, which would pull all
   ratios toward 1 (`work=8`: C2/Go falls from 1.73 to 1.31).
2. **The shared-table synchronisation differs per language.** Counted readers of a shared table need load+increment to be atomic, so
   the C/Rust/Go versions take a stripe lock, while Java reads a `ConcurrentHashMap` with no lock and no count. My C lock is an exclusive spinlock;
   Go and Rust use reader-writer locks. This is why hot_same results are not comparable across languages and why Rust idiomatic is
   slower than C2 in W3. A refcounted design genuinely needs something like this (hazard pointers, RCU or a lock), so it is a cost of the model,
   but my particular lock is not a fair stand-in for what Gort would ship.
3. **C2 and C4 are hand-defined.** What counts as a "pass" (I count every call argument and every field load into a local, plus store-into-field
   as clone+drop) decides C2's traffic (33 incs/request); C4's elisions were chosen by me and are an upper bound on what an optimiser recovers.
   Under a different convention C2 would look better or worse, but the W3 result has headroom: even C3, with *all* counts atomic, ties Go.
   (W5 adds a fourth issue: the load generator saturated before the C servers did.)

## 1.5 Where Gort's overhead really comes from

On this hardware the cost of refcounting everywhere is not the counting. Non-atomic inc/dec is nearly free because it overlaps with call and
memory latency (W1: +0.0-0.03 ns/pass; W3: 8% over raw including the flag test), the flag test is a predictable branch, and the compiler-level
elision of those pairs recovers only a few points more. The overhead is concentrated in three other places: (1) **atomic operations on
objects that really are shared**: ~3.7 ns each, uncontended, so a design that flags an object shared and then passes it around freely pays
~7.4 ns per pass, 10x a local pass (W1 shared=1, W2 single thread 4x below raw, C3 in W3 0.59x of C2); the thing to minimise is the number of
*flagged* objects and the number of passes of them, not the flag test; (2) **contention on hot shared objects and shared-table reads**: counted readers must
synchronise (a lock or equivalent) in order to clone safely, and a single hot object collapses to a few Mops/s for any implementation that does so
(W2 hot_same, where raw C collapses too); (3) **per-object malloc/free with a cascading destructor**, which is not a counting cost but is where a
refcounting runtime loses to a bump-allocating generational GC (W4: Java G1 5x faster; W4 C free ≈ 10 ns/node), and which a Gort runtime could attack with a better
allocator or arenas. For request-shaped server code with request-local objects, the model is viable by the pre-registered measure;
the open risks are shared mutable state and allocation-heavy graphs, not the pass traffic.

## 1.6 Not measured

CPU counters (no `perf`); fixed frequency or SMT-off runs; any second machine; a real Gort compiler (the C is hand-written and C4's elisions are
mine); real network beyond loopback and any C-server difference in W5 (generator-limited); W2 with C1 at >1 thread (unsound) and Java ZGC W2 at 2 and 4
threads; Rust `rust-box` with a weak parent (not expressible); RSS for Java as a measure of live data (heap sizing dominates); queueing latency
under offered load (all latencies are closed-loop service times); verification of Go/Java escape analysis behaviour (assumed from design, see METHODOLOGY.md).
